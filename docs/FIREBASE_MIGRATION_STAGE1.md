# Firebase + Cloud Run migration assessment — Stage 1

Status: historical Stage 1 assessment. Stage 2 has replaced the local Supabase implementation; this document is retained as the original migration decision record.

## Decision summary

Firebase Authentication can replace the current customer login/session provider. Cloud Firestore can replace customer-facing operational data. Cloud Run should host the Next.js/API application and dedicated webhook/worker services. Cloud Tasks, not Firestore polling, should become the durable delivery queue.

The existing Meta implementation remains conceptually unchanged: OpenDM owns one Meta application; a signed-in customer authorizes their own Instagram Professional account; encrypted account tokens remain server-only; a webhook resolves the Instagram account before evaluating tenant automations.

## Current Supabase audit

### Authentication and session handling

- Browser and server sessions use `@supabase/ssr` in `src/lib/supabase/clients.ts`, `src/middleware.ts`, and `src/app/auth/callback/route.ts`.
- Historical note: the pre-migration application included several non-Google authentication flows; these were removed for the final Google-only design.
- Route handlers accept a Supabase bearer JWT or session cookies through `src/lib/auth.ts`. That module also looks up `profiles.role` and `profiles.account_status`; suspended customers are denied.

### PostgreSQL / RLS / migration model

The schema is in five SQL migrations under `supabase/migrations/`:

| Current object | Current responsibility | Firestore / Cloud Run replacement |
| --- | --- | --- |
| `profiles` + `auth.users` trigger | Customer profile, role, active/suspended status | Firebase Auth UID + `customers/{uid}` |
| `instagram_accounts` | Tenant-owned Instagram identity and encrypted token | `instagramAccounts/{accountId}` plus server-only IGSID lookup |
| `automations` | Tenant/account automation configuration | `automations/{automationId}` |
| `contacts` | Per-account audience CRM | `instagramAccounts/{accountId}/contacts/{audienceIgsid}` |
| `automation_sessions`, `dm_logs` | Two-step/opening/follow-first session state and transcript | `automationSessions/{sessionId}` and `automationSessions/{sessionId}/messages/{messageId}` |
| `dm_jobs`, `dm_sent_log`, `job_queue` | Delivery audit, deduplication, retry queue | Firestore audit/dedupe documents + Cloud Tasks |
| `dm_rate_events` | Per-account rolling rate limit | Server-side Redis/Memorystore preferred; Firestore fallback needs sharded counters/leases |
| `debug_events` | Diagnostic stream | `debugEvents/{eventId}` with owner/account fields and TTL |
| `app_settings` | Historical platform Meta config | Already replaced in source by server environment variables; do not migrate secrets to Firestore |
| `subscription_plans`, `customer_subscriptions`, `usage_counters`, `admin_audit_logs` | SaaS plans, limits, admin actions | Top-level Firestore collections, server-only mutations |

Existing RLS is the first line of client data isolation for profiles, accounts, automations, contacts, sessions, logs, subscriptions, and usage. Service-role calls deliberately bypass RLS but route handlers independently verify ownership. The Firebase target must preserve both layers: restrictive Firestore rules and server-side ID-token verification/ownership checks.

### Server-side automation dependencies

- `src/lib/automation/processWebhook.ts`: resolves Meta `entry.id` to the internal Instagram account, then scopes automation lookup by account.
- `src/lib/automation/processJob.ts`: performs delivery-window checks, dedupe, rate limiting, encrypted-token use, DM logging, session state, and follow-first verification.
- `src/lib/automation/queue.ts`: uses unique `dedupe_key`, `FOR UPDATE SKIP LOCKED`, and retry state.
- `src/lib/automation/engine.ts`: sequentially drains jobs, applies Meta error classification, retries, and circuit-breaker behavior.
- `src/app/api/cron/process-jobs/route.ts`: token refresh, delayed-job drain, and cleanup.
- Supabase Storage currently holds public card images from `src/hooks/useAutomations.ts`.

## Target Firestore data model

Use Firebase Auth UID as `ownerId`. All IDs generated by the server are opaque IDs, never customer-supplied ownership identifiers. Persist timestamps as Firestore `Timestamp` values.

```text
customers/{uid}
  displayName, email, role: customer|admin, accountStatus: active|suspended,
  subscriptionId, createdAt, updatedAt

instagramAccounts/{accountId}
  ownerId, instagramUserId, username, profilePictureUrl,
  accessTokenEncrypted, tokenExpiresAt, isActive, pausedUntil, pauseReason

instagramAccountLookup/{instagramUserId}
  accountId, ownerId, active

automations/{automationId}
  ownerId, accountId, type, isActive, postId, keywords, responses,
  askToFollow*, totalDmsSent, createdAt, updatedAt

instagramAccounts/{accountId}/contacts/{audienceIgsid}
  ownerId, username, followsBusiness, firstInteractionAt,
  lastInteractionAt, lastAutomationId, totalTriggers

automationSessions/{sessionId}
  ownerId, accountId, automationId, audienceIgsid, currentStep,
  completed, expiresAt, startedAt, lastActivityAt
automationSessions/{sessionId}/messages/{messageId}
  ownerId, direction, step, messageText, sentAt

deliveryDedupe/{sha256(accountId + automationId + eventId)}
  ownerId, accountId, automationId, triggerUserId, eventId, createdAt
deliveryAudienceDedupe/{sha256(accountId + automationId + audienceIgsid)}
  ownerId, accountId, automationId, audienceIgsid, createdAt
deliveryJobs/{jobId}
  ownerId, accountId, automationId, type, payload, taskName,
  status, attempts, runAfter, lastError, createdAt, updatedAt
deliveryAudit/{eventId}
  ownerId, accountId, automationId, triggerEventId, status, metadata, createdAt
debugEvents/{eventId}
  ownerId, accountId, service, level, eventType, status, message, metadata, createdAt, expiresAt

plans/{planId}
customerSubscriptions/{uid}
usageCounters/{uid}/months/{yyyyMM}
adminAuditLogs/{logId}
```

### Important model decisions

1. Keep `instagramAccounts` and `automations` top-level. The webhook needs a direct server-side IGSID lookup and the worker needs account-scoped automation queries without reading another tenant.
2. Use the `instagramAccountLookup` document only from Cloud Run/Admin SDK code. It prevents a collection scan for every webhook and has a uniqueness-like role that Firestore does not provide natively.
3. Store encrypted tokens only in `instagramAccounts`; never send this document to the browser. Keep the existing AES-256-GCM encryption mechanism and put its key in Secret Manager, not Firestore.
4. Keep image bytes in Cloud Storage, not Firestore. Store only an object path or a controlled public URL in the response card.
5. Do not put an unbounded message history, raw webhook body, or large image base64 content in a single Firestore document. Firestore has document and index limits.

These are the initial expected query indexes. Confirm generated index links under the Firebase Emulator and staging workload before production deployment.

| Collection | Fields | Purpose |
| --- | --- | --- |
| `instagramAccounts` | `ownerId ASC, isActive ASC, createdAt DESC` | Customer account list |
| `instagramAccounts` | `isActive ASC, tokenExpiresAt ASC` | Server-only token refresh scan |
| `automations` | `ownerId ASC, accountId ASC, createdAt DESC` | Customer automation list |
| `automations` | `accountId ASC, isActive ASC, type ASC` | Webhook trigger matching |
| `deliveryJobs` | `status ASC, runAfter ASC` | Operations/audit view only; Cloud Tasks is the execution source |
| `deliveryAudit` | `ownerId ASC, createdAt DESC` | Customer execution history |
| `debugEvents` | `ownerId ASC, createdAt DESC` | Tenant debug panel |
| `adminAuditLogs` | `targetUserId ASC, createdAt DESC` | Admin customer detail |

Disable indexing for large `payload`, raw Meta payload, long message/card bodies, and debug metadata unless an actual query requires them. Index entries consume storage and query cost.

## Security and authorization model

### Browser

- Firebase Auth handles Google sign-in and client auth-state observation.
- The web client obtains a Firebase ID token and sends it as `Authorization: Bearer <token>` to OpenDM API routes.
- The Cloud Run API verifies it with Firebase Admin `verifyIdToken`; it derives the UID only from the verified token.
- Customer-facing writes remain API-mediated during the migration. This preserves Zod validation, plan enforcement, Meta token protection, and audit logs.

### Cloud Run server

- Attach a dedicated least-privilege service account. Use Application Default Credentials; do not deploy a service-account JSON key or `FIREBASE_ADMIN_PRIVATE_KEY` as an environment variable.
- Use Firebase custom claims only for coarse `admin` role hints. The canonical customer state (`role`, `accountStatus`) remains in `customers/{uid}` and is checked server-side for each sensitive request.
- The server must check `ownerId === verifiedUid` on every customer account, automation, contact, session, log, and subscription operation. Never trust `ownerId`, `accountId`, or `uid` from body/query input.
- Admin APIs require both a verified token and server-validated active admin role. All admin mutations create an `adminAuditLogs` document.

### Proposed Firestore rules

The preferred Stage 2 posture is **server-only access** for sensitive operational collections. These rules are intentionally restrictive; Cloud Run Admin SDK bypasses rules, so IAM and route authorization remain mandatory.

```rules
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    function signedIn() { return request.auth != null; }
    function own(uid) { return signedIn() && request.auth.uid == uid; }

    match /customers/{uid} {
      allow read: if own(uid);
      allow update: if own(uid)
        && request.resource.data.role == resource.data.role
        && request.resource.data.accountStatus == resource.data.accountStatus;
      allow create, delete: if false;
    }

    // API/Cloud Run only: avoids browser access to encrypted tokens, job
    // payloads, audit/debug data, tenant data, and admin data.
    match /{document=**} { allow read, write: if false; }
  }
}
```

Cloud Storage follows the same principle: use Cloud Run-issued upload handling or tightly scoped paths such as `card-images/{uid}/{object}`. Do not grant cross-tenant public write/list access.

## Queue, retries, spikes, and Cloud Run

### Recommended request path

1. A small Cloud Run **webhook service** receives Meta’s event, verifies the raw-body HMAC, resolves `instagramAccountLookup/{IGSID}`, validates tenant/account state, records dedupe atomically, creates audit state, enqueues a Cloud Task, and returns HTTP 200 quickly.
2. A dedicated Cloud Run **worker service** receives the authenticated Cloud Task request. It re-reads account/automation/session state, applies the existing 24-hour window, follow-first verification, per-account Meta rate limit, jitter, and circuit breaker, then records delivery outcome.
3. Cloud Tasks handles delayed retries and explicit max attempts. It is the durable scheduler. A task must be idempotent because queue delivery is at-least-once.
4. Cloud Scheduler invokes a maintenance Cloud Run endpoint/job for token refresh, TTL cleanup verification, and stalled-job reconciliation. It never replaces the task queue.

### Deduplication and rate control

- Before queueing, use a Firestore transaction to create `deliveryDedupe` and audience-level dedupe records; if either exists, acknowledge the webhook without a task.
- The worker repeats the dedupe check before Meta send. Write an audit record with Meta message ID only after a successful send.
- Retain the existing circuit breaker and jitter exactly. A button click is not follow verification; only a Meta `true` status may release a follow-gated response.
- Do not emulate the Postgres rolling-window rate query with a hot single Firestore counter. Prefer Memorystore/Redis for atomic rolling-window rate limiting. If Redis is not approved, use a carefully sharded Firestore counter plus transaction/lease design and load test it before enabling production sends.

### Sudden traffic spikes and cost controls

- Set Cloud Run webhook concurrency separately from the worker. The webhook can be moderately concurrent because it only validates/enqueues; keep worker concurrency low enough to preserve Meta pacing.
- Set Cloud Tasks queue dispatch-rate and concurrent-dispatch limits, and use exponential retry with a dead-letter workflow for terminal failures.
- Begin with a Cloud Run service-level maximum instance cap (for example 3), observe queue depth/latency/error rate, then raise deliberately. A cap constrains cost but can create backlog, which is acceptable because Cloud Tasks retains work.
- Set min instances to `0` initially to avoid idle cost unless cold-start measurements demand otherwise.
- Enable Cloud Billing budgets/alerts, Cloud Run request/error/instance metrics, Cloud Tasks queue depth/oldest-task alerts, Firestore read/write dashboards, and structured logs with tenant/account IDs redacted or hashed as needed.
- Use Firestore TTL on short-lived debug, dedupe, and delivery audit documents; exclude verbose payload fields from indexes.

## Firebase project setup instructions

1. In the [Firebase console](https://console.firebase.google.com/), create a project or add Firebase to the Google Cloud project intended for OpenDM. Pick a region close to the eventual Cloud Run region; Firestore region cannot be casually changed later.
2. Register a **Web app** named `OpenDM Web`. Copy the Firebase web configuration values into local `.env` only:
   - `NEXT_PUBLIC_FIREBASE_API_KEY`
   - `NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN`
   - `NEXT_PUBLIC_FIREBASE_PROJECT_ID`
   - `NEXT_PUBLIC_FIREBASE_STORAGE_BUCKET`
   - `NEXT_PUBLIC_FIREBASE_MESSAGING_SENDER_ID`
   - `NEXT_PUBLIC_FIREBASE_APP_ID`
3. In **Authentication → Sign-in method**, enable Google. Add the local and future production domains to Authorized domains.
4. Create Firestore in **Production mode**. Do not use test-mode rules for a multi-tenant deployment. Stage 2 will add the reviewed rules and indexes through the Firebase CLI.
5. Enable Cloud Storage only if card-image uploads remain enabled. Keep it in the same project and use restrictive storage rules.
6. For Cloud Run, create a dedicated runtime service account later with only the Firebase Admin/Firestore, Secret Manager, Cloud Tasks enqueuer/worker, Storage, and logging permissions it needs. Cloud Run should use this identity rather than a downloaded service-account key.
7. Keep these private values in Secret Manager during Stage 2/deployment: `TOKEN_ENCRYPTION_KEY`, `CRON_SECRET`, `META_INSTAGRAM_APP_SECRET`, optional `META_FACEBOOK_APP_SECRET`, and `META_WEBHOOK_VERIFY_TOKEN`.

The Firebase web config is not a service-account credential, but restrict its API key in Google Cloud and never mistake it for a security boundary. Authorization comes from Firebase Auth, Firestore rules, Cloud Run token verification, and IAM.

## Safe staged migration plan

### Stage 1 — current stage

- Complete inventory, target schema, rules/index draft, queue design, and Firebase project preparation.
- Preserve current Supabase behavior. Do not install SDKs, delete code, deploy rules, or migrate data.

### Stage 2 — implementation after approval

1. Add Firebase client/admin SDK adapters beside (not replacing) `src/lib/supabase`.
2. Implement Firebase Auth with a feature flag and verify Firebase ID tokens in server routes.
3. Introduce Firestore repository interfaces for profiles/accounts/automations/contacts, preserving API contracts and Zod schemas.
4. Add Cloud Storage adapter for card images, Cloud Tasks adapter for jobs, and Firestore/Redis implementations for dedupe/rate limits.
5. Migrate unit/integration tests to Firebase Emulator Suite and Cloud Tasks test doubles.

### Stage 3 — data and auth cutover

1. Back up/export Supabase Postgres and Storage; record row counts/checksums per tenant.
2. Re-encrypt nothing unnecessarily: copy already encrypted Instagram token values only if `TOKEN_ENCRYPTION_KEY` remains unchanged and controlled. Otherwise require secure reconnection.
3. Existing users must authenticate through the approved Google provider; do not attempt an unsupported credential migration.
4. Import tenant documents in idempotent batches, validate owner/account/automation/contact/session counts, then dual-read or shadow-read in staging.
5. Test two Firebase customers, two Instagram accounts, authorization denials, webhook routing, duplicate webhook delivery, follow-first unknown status, rate limits, retries, token refresh, suspension, and plan caps.
6. Cut over only after metrics and reconciliations pass. Retain Supabase read-only rollback access for an agreed window before decommissioning.

## Stage 1 exit criteria

- Firebase project exists, region selected, and public web configuration is available locally.
- No secret has been committed.
- Firestore is in production mode; rules/index files are reviewed before deployment.
- Cloud Run service-account/IAM and Cloud Tasks queue choices are approved.
- The owner approves Stage 2 implementation.
